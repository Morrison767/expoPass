# QazExpoPass — кликабельный прототип

Прототип информационного сервиса электронных пропусков АО «НК «QazExpoCongress».
Реализован **Этап 1** технического задания — материальный пропуск на внос и вынос ТМЦ.

Бэкенда нет: пользователи, объекты и заявки живут в `localStorage` и засеиваются
при первом запуске.

## Демонстрация

Прототип опубликован на GitHub Pages — ссылка в описании репозитория.
Данные хранятся в localStorage браузера, поэтому у каждого посетителя
своя независимая копия: можно свободно создавать заявки и согласовывать их,
не мешая другим.

## Локальный запуск

```bash
npm install
npm run dev
```

Откройте <http://localhost:3000>.

## Публикация

`npm run build` собирает статический экспорт в каталог `out` — бэкенда
у прототипа нет, поэтому он раздаётся как обычный набор файлов.
Публикация выполняется автоматически при пуше в `main`
(см. `.github/workflows/deploy.yml`).

Чтобы сбросить данные к начальному состоянию — очистите ключ `qazexpopass-store`
в localStorage и перезагрузите страницу.

## Стек

| Слой | Решение |
| --- | --- |
| Каркас | Next.js 14 (App Router), TypeScript |

| Компоненты | shadcn/ui поверх Radix (dialog, select, checkbox, tabs) |

| Анимации | framer-motion |

| Состояние | Zustand + `persist` в localStorage |

| Шрифты | IBM Plex Sans / IBM Plex Mono через `next/font` |

## Что реализовано

**Процесс материального пропуска целиком:**

1. **Мастер создания заявки** — пять шагов «Данные → ТМЦ → Подтверждение личности →
   Проверка → Отправка» с анимированными переходами и прогресс-баром. Состояние держит
   react-hook-form, валидацию — zod по каждому шагу отдельно, поэтому возврат назад
   ничего не теряет. Ф.И.О., организация и e-mail подставляются из профиля, подмена
   заявителя запрещена. Операция — два крупных взаимоисключающих переключателя,
   дата действия — ровно одна (диапазон «с/по» отсутствует в модели данных).
   Параметр `?from=<id>` предзаполняет форму из возвращённой заявки.
2. **Таблица ТМЦ** — строки добавляются и удаляются с анимацией, минимум одна позиция,
   количество больше нуля, единицы измерения из справочника, счётчик позиций в шапке.
   Фотографии загружаются перетаскиванием, показываются миниатюрами и открываются
   в полный размер; перед сохранением изображение ужимается до 480px — иначе
   localStorage не выдерживает снимков с телефона.
3. **Подтверждение личности** — взаимоисключающее правило п. 8.5, вынесенное
   в отдельный шаг с наглядным сравнением двух веток:
   - чекбокс не установлен → требуется ЭЦП, без подписи отправка заблокирована;
   - чекбокс установлен → блок загрузки паспорта появляется автоматически,
     без файла отправка заблокирована, ЭЦП не требуется.

   Подписание ЭЦП — окно-эмуляция: хэш SHA-256 подписываемых данных, последовательная
   проверка сертификата, затем сведения о сертификате (владелец, замаскированный ИИН,
   серийный номер, срок действия). Изменение данных после подписания требует повторной ЭЦП.
4. **Маршрут** — администратор объекта (согласовать / вернуть / отклонить) →
   Главный оперативный центр (регистрация). Возврат и отклонение требуют комментария.
5. **Регистрация** — присвоение уникального номера, статус «Действует», запись в реестре.
6. **Итоговый документ** — PDF-представление с логотипом, отметками подписания,
   согласования и регистрации, перечнем ТМЦ и QR-кодом. Паспорт нерезидента в документ
   не попадает — только отметка о подтверждении личности.
7. **QR-проверка** — QR на документе ведёт на `/verify/<номер>`: камера открывает
   страницу сразу, без ввода. Статусы «ДЕЙСТВИТЕЛЕН», «ИСТЁК», «АННУЛИРОВАН»,
   «НЕ НАЙДЕН». Экран изолирован от кабинета — свой каркас, без бокового меню
   и без авторизации. ИИН, паспорт, телефон и e-mail не раскрываются,
   Ф.И.О. показывается фамилией с инициалами.
8. **Реестр** — колонки по минимальному перечню п. 8.12, поиск, фильтры по статусу,
   операции и объекту, сортировка, постраничный вывод. Экспорт в XLSX (SheetJS,
   с шириной колонок и автофильтром) и в CSV — выгружается ровно то, что осталось
   после отбора.
9. **Администрирование** — справочник объектов с наименованиями KZ/RU/EN, порядком
   отображения, деактивацией и назначением ответственного согласующего; управление
   учётными записями, ролями и закреплением за объектами.
10. **Аудит** — каждое действие пишет запись в таймлайн заявки: кто, когда, что,
    с комментарием.

**Ролевая модель.** Категория пользователя и системная роль хранятся раздельно,
у одного пользователя может быть несколько ролей — в шапке есть переключатель.
Состав меню, сводки и доступных действий зависит от активной роли; заявитель видит
только свои заявки, администратор объекта — только свои объекты.

**Автоматический переход в «Истекла».** При входе пересчитываются зарегистрированные
пропуска с прошедшей датой; записи из реестра не удаляются.

**Регистрация и её рассмотрение:**

1. **Форма `/register`** — Фамилия / Имя / Отчество отдельными полями, e-mail с проверкой
   формата и уникальности, телефон с маской и кодом страны, категория пользователя.
   Организация показывается и становится обязательной по категории, объект размещения —
   мультивыбор, обязателен только для арендатора. Пароль с подтверждением и наглядной
   проверкой сложности. Согласие на обработку персональных данных обязательно, текст
   открывается в диалоге; фиксируются дата, время и версия редакции.
2. **Подтверждение e-mail** — шестизначный код, демонстрационное значение `123456`
   подсказано на экране. Учётная запись создаётся только после верного кода.
3. **Экран `/register/pending`** — что уже сделано и что будет дальше; вход закрыт до
   решения администратора.
4. **Очередь `/admin/registrations`** — вкладки «Ожидают подтверждения» и «На уточнении»,
   карточка с полными данными. Администратор подтверждает, отклоняет с обязательной
   причиной либо возвращает на уточнение с обязательным комментарием; перед подтверждением
   может поправить категорию, организацию, объекты и назначить дополнительные роли.
5. **Уведомления** — решение по регистрации приходит в колокольчик в шапке; администраторы
   получают уведомление о каждой новой регистрации.
6. **Вход `/login`** — форма e-mail + пароль и быстрый вход карточкой для демонстрации.
   Неактивная учётная запись не пускает и объясняет причину: ждёт подтверждения,
   требует уточнения, отклонена с указанием причины, заблокирована.

## Что намеренно не реализовано

Прототип кликабельный и без бэкенда, поэтому вне объёма остались:

- реальная авторизация, пароли, подтверждение e-mail, двухфакторная аутентификация;
- фактическая интеграция ЭЦП — подписание имитируется, механизм согласовывается
  с Заказчиком на этапе проектирования;
- реальная загрузка файлов и антивирусная проверка — вложения регистрируются
  как метаданные;
- отправка электронной почты — в интерфейсе показано, что письмо уходит;
- переводы KZ/EN — переключатель языка работает и сохраняет выбор, тексты
  подключаются отдельным этапом;
- Этап 2 (наряд-допуск) и Этап 3 (гостевой пропуск, ГБД ФЛ).

## Дизайн-система

Визуальный слой перенесён из действующего проекта Общества — ИС учёта мероприятий
(`Desktop/експо`). Перенесены токены и презентационные компоненты; бизнес-логика,
роуты и стейт-менеджмент старого проекта не заимствовались.

**Цвета.** Ink Navy (`#1B3A6B` — primary), Obsidian (корпус каркаса, `#080D14`),
Beam Cyan (свет и фокус: `#0B7C93` на светлой теме, `#35D6F0` на тёмной),
Signal Amber, нейтральная шкала Ink, палитра из 8 статусных токенов.
Всё через семантические CSS-переменные — светлая и тёмная темы обслуживаются
одними классами.

**Типографика.** IBM Plex Sans и IBM Plex Mono, базовый кегль интерфейса 13px,
CAPS-метки 10px с трекингом `0.12em`, табличные цифры в таблицах и полях ввода.

**Приёмы.** Светящаяся кромка статуса слева от карточек и строк реестра,
фокус-кольцо цвета луча, трёхслойная глубина поверхностей (градиент + фаска + тень),
точечная фактура на каркасе, сдержанные радиусы 3–8px.
